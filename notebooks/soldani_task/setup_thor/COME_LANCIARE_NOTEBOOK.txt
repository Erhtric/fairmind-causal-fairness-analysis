=======================================================================
COSE GIA' SISTEMATE (non serve piu' pensarci)
=======================================================================

- run_benchmark.sbatch / run_multimodal.sbatch non chiedono piu' una
  GPU propria: riusano il server gia' attivo (nome job corretto:
  llama_server_gpu), niente piu' PENDING per contesa GPU.
- La ricerca del server con squeue non usa piu' "-u $USER": dentro un
  job batch la risoluzione dell'utente via NSS/LDAP a volte fallisce
  ("squeue: error: Invalid user: marco.soldani") anche se l'utente e'
  valido, facendo fallire lo script con un falso "nessun server trovato"
  anche quando il server e' attivo. Ora si cerca solo per nome del job.
- apptainer exec (nell'esecuzione del notebook) aggiunto --no-home: per
  lo stesso motivo NSS/LDAP, apptainer falliva con "Couldn't determine
  user account information" prima ancora di entrare nel container. In
  piu' lo script non controllava l'exit code di questo comando: il job
  finiva con ExitCode 0:0 ("Benchmark completato") anche se il notebook
  non era mai stato eseguito e nessun file di output era stato creato.
  Ora, se apptainer/jupyter falliscono, il job termina con errore vero.
- CAUSA RADICE trovata il 20/07/2026: sui nodi della partition "compute"
  la risoluzione utente via NSS/LDAP dentro un job batch e' rotta —
  anche un semplice `whoami` fallisce con "cannot find name for user ID
  30117812", non e' un problema di apptainer o dei nostri script.
  Confermato con un job di debug: su "compute" whoami/apptainer falliscono
  sempre (con o senza --no-home/--fakeroot); sulla partition "gpu" invece
  funzionano perfettamente. run_benchmark.sbatch e run_multimodal.sbatch
  ora girano su partition=gpu SENZA --gres=gpu:1 (non consumano una GPU,
  solo CPU/mem) — questo evita sia il bug NSS sia il problema originale
  di PENDING per contesa GPU. Se in futuro capita di nuovo un errore
  "unknown userid" o "Couldn't determine user account information" su
  QUALSIASI partition, e' probabilmente lo stesso problema di infra
  del cluster: vale la pena segnalarlo ai sysadmin di Thor piuttosto
  che continuare a cercare fix lato script.
- llama_server.sbatch nel repo ora rispecchia esattamente lo script
  realmente usato su Thor (partition gpu, modello 14B, container
  llama_server_gpu.sif, --time 14 giorni) — prima il file nel repo
  descriveva una configurazione mai usata davvero (gpuISIN, modello 7B).
- llama_server.def era incollato dentro un heredoc bash (`cat > ... <<
  EOF`) e non era un .def valido per apptainer build — ripulito e
  riallineato al contenuto reale verificato su scratch (il symlink
  libcuda.so.1 + i linker flags per lo stub CUDA, non solo LD_LIBRARY_PATH).
- jupyter_env.def: `pip install --no-cache-cdir` era un typo (flag pip
  inesistente, build avrebbe fallito subito) -> corretto in --no-cache-dir.

  sankey.py) e src.visualisation.graph, importati da

- I notebook leggono LLAMA_HOST/LLAMA_PORT dall'ambiente in automatico

TROUBLESHOOTING RAPIDO
=======================================================================

Job PENDING da un pezzo
  -> scontrol show job <jobid> e guarda il campo "Reason". I job
     automatici (compute, senza GPU) non dovrebbero piu' restare in
     coda per mancanza di risorse GPU.

"Connection error" nel notebook quando chiama il LLM
  -> il server llama_server_gpu non e' attivo, o LLAMA_HOST punta al
     nodo sbagliato. Rifai il PASSO 1 e ricontrolla l'hostname con
     `squeue -u $USER` (colonna NODELIST).

apptainer build fallisce con errori strani sulla prima/ultima riga
  -> controlla che il file .def non contenga righe tipo `cat > ... <<
     EOF` o `EOF` residue da un copia-incolla di terminale (era il bug
     di llama_server.def, ora corretto).
